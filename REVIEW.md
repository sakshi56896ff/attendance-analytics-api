# Code Review

I reviewed the starter `app/main.py` against the API contract in `openapi.yaml` and the data model notes. The main risk was that several paths worked only for a simple happy-path request, while the contract also covers pagination, concurrency, time zones, and larger datasets.

## Things I checked and did not treat as defects

- The API uses `employees` and `attendance_logs`, which matches `DATA_MODEL.md`.
- Calendar dates such as `date` and `joined_on` are stored as `YYYY-MM-DD` strings by design; they should not automatically be converted into timestamps.
- `status` defaults to `PRESENT` in the request model, which matches the documented default. The endpoint still needs to validate that only the permitted punch-in statuses are accepted.
- The API's use of FastAPI and PyMongo is suitable for this task; the problems were in the endpoint logic and contract coverage, not the framework choices.

## Verification note

This review describes defects found in the supplied starter file and the fixes intended for the completed implementation. Before submission, run the tests against the final saved `app/main.py`; a successful HTTP 200 alone does not verify the full business rules or query-plan requirements.
